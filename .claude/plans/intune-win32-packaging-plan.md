## Plan: Intune Win32 Packaging Flow

Extend the existing Intune reconciliation workflow in EvergreenUI so it can compare PSPackageFactory-managed Win32 apps in Intune against local App.json definitions, resolve the latest version from each manifest's Evergreen query, download/package the installer, import the Win32 app using the existing Connect-MgGraph-based authentication flow, and automatically supersede the previously matched PSPackageFactory app when the import represents an update.

**Steps**
1. Phase 1 - Stabilize the Intune comparison model. Reuse the existing reconciliation entry points in c:\projects\_EUCPilots\evergreen-ui\EvergreenUI\Public\Start-EvergreenWorkbench.ps1, especially parseComparableVersion, loadIntuneDefinitions, loadIntuneWin32Apps, and refreshIntuneComparison. Refactor the in-file comparison shaping into private helper functions so the same match model can drive the table, action enablement, and later package/import operations. This phase blocks all later phases because the actionable row model is the source of truth.
2. Add a normalized comparison/action row contract for the Intune workflow. Each row should carry definition path, parsed App.json object, package type, current manifest version, latest Evergreen version, matched Intune app id, matched Intune displayVersion, import mode (New or Update), and a validation/actionability state. Preserve the current PSPackageFactory Notes matching behavior based on CreatedBy=PSPackageFactory and Guid in notes JSON, because that matches the upstream Create-Win32App note format.
3. Phase 2 - Introduce private packaging/import helpers in EvergreenUI/Private. Add Get-IntunePackageDefinitions to read App.json files and return enriched definition rows; Get-IntunePackageLatestVersion to evaluate Application.Filter from App.json via Get-EvergreenApp or Get-VcList and produce the resolved artifact metadata; Invoke-IntunePackageBuild to prepare the working folder, download the latest installer, stage Install.ps1 or PSAppDeployToolkit content, and create the .intunewin via New-IntuneWin32AppPackage; Invoke-IntuneGraphWin32Import to create the Intune app through Microsoft Graph using the existing Connect-MgGraph session; Set-IntuneGraphWin32Supersedence to link the newly imported app to the matched prior PSPackageFactory app through Graph relationships. Steps 3-5 in this phase can share parsing logic but should be implemented as separate helpers for testability.
4. Reuse the upstream PackageFactory behavior selectively instead of vendoring its full script set. Mirror the support/New-Win32Package.ps1 flow for working folders, source content, installer staging, and signing hooks, but implement the missing Create-Win32App behavior natively inside EvergreenUI against Microsoft Graph so the UI does not depend on a non-repo external script or IntuneWin32App's separate authentication model. Preserve the upstream Notes JSON shape with CreatedBy, Guid, and Date, and map App.json Information, Program, RequirementRule, DetectionRule, Dependencies, and Assignments into the Graph import helper. Treat upstream Supersedence data as out of scope for the initial import path because the chosen requirement is automatic latest-over-previous supersedence based on the matched app in Intune.
5. Phase 3 - Expand the existing UI workflow in Start-EvergreenWorkbench. Keep IntuneRefreshCatalogButton wired to loadIntuneWin32Apps, but change the package/import action path from placeholders to real orchestration. Replace startIntuneImportOperation with a more general background runner that accepts action mode and selected reconciliation rows, then calls the new private helpers in a runspace. Enable actions from the reconciliation table rather than from separate definition/package lists. Because the decision is selected rows only, change IntuneWin32AppsListView from Single to Extended selection and add selection-based button state logic so only rows marked Import as new app or Update app are actionable. The runner must also drive the existing Intune loading/status UI so long-running actions visibly report the current stage in the tab while they execute.
6. Add a packaging and import pipeline that runs per selected row. For each selected actionable row, load the definition, resolve the latest version from Application.Filter, compare latest version to both manifest version and matched Intune version, update the in-memory package payload for this run, download the latest installer, create the .intunewin file in the configured output/working path, import the new app into Intune, and if the row is an update configure the new app to supersede the previous matched app. This step depends on phases 1-3 and should support sequential execution with aggregated progress/log output rather than parallel execution, because the current WPF runspace pattern and Intune module calls are simpler and safer sequentially. Each major stage must update the visible Intune status label/loading panel and emit a corresponding progress log entry, including the action name, current row/app, command or API step being executed, success milestones, warnings, and terminal errors.
7. Phase 4 - Define the exact import/update behavior. For new apps, always create a fresh Win32 app with PSPackageFactory Notes. For updates, also create a fresh Win32 app rather than mutating the existing app package in place, then configure supersedence from the new app to the matched prior app. Use the previous app selected by GUID match and highest comparable displayVersion. If multiple Intune apps share the same PSPackageFactory Guid, mark the row Needs review and block import until the ambiguity is resolved.
8. Build prerequisite and guardrail checks before action execution. Require a valid Intune sign-in via requireImportAuth and a loaded IntuneWin32App module for packaging. Add explicit validation for missing definitions path, missing package output path, invalid App.json, missing PSPackageFactoryGuid, unsupported filter command, failed latest-version resolution, download failure, missing detection/program metadata needed for Graph import, and supersedence targets that cannot be identified uniquely. Also add a Graph scope check up front so the existing Connect-MgGraph session has the app-management permissions needed for create, update, and relationship operations.
9. Phase 5 - Persist and expose any new Intune settings. Extend Get-UIConfig and Set-UIConfig if the implementation needs additional path or behavior settings beyond DefinitionsPath and PackageOutputPath, for example a working folder, signing certificate selection, or PSAppDeployToolkit path. If those settings are not required in the first pass, keep the schema unchanged and derive working paths beneath PackageOutputPath to avoid unnecessary UI scope expansion.
10. Phase 6 - Add tests around pure logic and config behavior. Expand tests/EvergreenUI.tests.ps1 with coverage for config defaults/merging, definition parsing, notes/GUID matching, comparable version handling, latest-version actionability decisions, and supersedence target selection. Keep UI event wiring and interactive Intune cmdlet execution out of automated tests; cover those with a manual verification checklist.
11. Phase 7 - Manual validation and regression pass. Validate module loading, sign-in gating, definition loading, reconciliation output, package creation for both new and update rows, Intune import success, and automatic supersedence creation against a test tenant. Confirm that non-actionable rows remain blocked, existing Nerdio behavior is unchanged, and logs remain readable during long-running package/import runs.

**Decisions**
- Import path: implement the missing Create-Win32App behavior directly inside EvergreenUI using the existing Connect-MgGraph session for Intune CRUD operations while still using IntuneWin32App for packaging helpers where it does not impose its separate authentication model.
- Action model: operate on explicitly selected reconciliation rows, not all actionable rows by default.
- Supersedence model: for update rows, automatically configure the newly imported app to supersede the matched previous PSPackageFactory app.
- Matching model: keep using PSPackageFactory Notes JSON in Intune and Information.PSPackageFactoryGuid in App.json as the canonical linkage.
- Update model: create a new Win32 app for updated versions, then supersede the previous matched version, instead of updating the existing app package in place.

**Scope boundaries**
- Included: comparison of local App.json definitions to PSPackageFactory-managed Intune Win32 apps, latest-version resolution from Application.Filter, installer download, .intunewin packaging, Intune import, and automatic supersedence for updates.
- Included: minimal UI changes necessary to make reconciliation rows actionable and to surface progress/errors.
- Excluded from first pass: broad new settings UX for signing certificates/toolkit paths unless implementation proves they are required, Graph-only import reimplementation, assignment-management redesign, and general support for non-PSPackageFactory Intune apps.
- Excluded from first pass: honoring arbitrary App.json Supersedence arrays beyond the automatic previous-version link, unless the existing IntuneWin32App cmdlet surface makes that nearly free after the core flow is working.

**Further considerations**
1. IntuneWin32App still remains useful for local packaging, but its authenticated cmdlets validate module-specific globals created by Connect-MSIntuneGraph. Because the chosen direction is to keep Connect-MgGraph as the only auth flow, the implementation should avoid those authenticated cmdlets and perform Intune CRUD and supersedence via Graph requests or Graph-backed helpers that reuse the existing session and scope model.
2. If packaging needs reusable helper assets such as Install.ps1 or PSAppDeployToolkit that are not yet part of this repo, decide whether to vendor the minimum required assets or limit the first pass to package definitions that already contain complete Source content.
3. If automatic latest-version resolution should also update the on-disk App.json manifest, treat that as a separate follow-up. The current request can be satisfied by runtime resolution and packaging without mutating source definitions.
